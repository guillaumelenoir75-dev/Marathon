# Plan Marathon — contexte projet

PWA de préparation marathon, multi-utilisateur. L'admin crée les comptes et a accès au Coach IA. Les athlètes suivent leur plan.

## Stack
- **Frontend** : `public/index.html` — HTML + CSS inline, charge 23 scripts JS via `<script defer>`.  
  Build : Vite (`root: 'public'`, `publicDir: '../public-static'`) → `dist/`. Les fichiers `public-static/src/*.js` sont copiés verbatim (pas de hash), chargés en scripts classiques (pas de modules ES). Toutes les fonctions doivent être en scope global.
  **Chargement** : `scriptFiles` (vite.config.js) → un seul `bundle-<n°>.js` ; écrans rares → `lazy-<groupe>-<n°>.js` (`lazyGroups` : `course` = race-nav-data + race-nav + race-map, `progress` = prep-progress, `whatif` = plan-whatif, `nextrace` = next-race, `planchat` = plan-chat), adresses dans `window.LAZY_BUNDLES` injecté dans dist/index.html, chargés par `lazyLoad(g)` (config.js) depuis des points d'entrée du même nom que la vraie fonction (`initRaceOrgMap`, `openProgress`, `openWhatIf`, `openNextRace`, `coachMode`, `coachModeInit`, `openPlanChat`, `pcSend` → `_lazyCall`) ; en dev, fichiers sources. Un module à la demande ne doit être appelé que sur action (jamais au démarrage) ; ses scripts ne sont pas dans index.html. Cache (firebase.json) : `/src/@(bundle|lazy)-*.js` = 1 an `immutable` (nom unique par version), le reste de `/src` sans cache. Chart.js en `defer`.
- **Backend** : Cloud Functions Firebase v2 (Node 24), modulaires dans `functions/`.
- **Données** : Firebase Realtime Database, projet `prepa-marathon` (europe-west1). Structure : `users/{uid}/state`, `users/{uid}/role`, `users/{uid}/preps/{id}` (copie figée d'une prépa) + `users/{uid}/prep_index/{id}` (fiche : nom, date, temps, bilan), `users/{uid}/prep_next` (prépa à venir : `meta` + `state` = clés de prépa, modifiable avant son début), `_push_subscribers/{uid}`.
- **Auth** : email / mot de passe. Création de comptes réservée à l'administrateur (ADMIN_UID).
- **Hébergement** : Firebase Hosting → https://prepa-marathon.web.app
- **Sécurité DB** : règles dans `database.rules.json` — chaque user ne lit/écrit que ses propres données, l'admin peut tout lire/écrire.

projection jusqu'au jour J avec les séances prévues (`fmRaceDay`, `fmPlanned`), affûtage conseillé (`fmTaperBest` : dernières semaines — marathon 3, autres 2 —, facteurs non croissants ≥ 40 / 45 / 50 %, pénalité au-delà de +25 de fraîcheur ; proposé seulement à ≤ 35 j de la course avec forme ≥ 20 et ≥ 42 j d'historique) appliqué par `fmApplyTaper` → `prApplyChanges` (kind `taper`, annulable) ; simulation de la semaine suivante ±20 %. `prApplyChanges(sel, meta)` (plan-review.js) = application commune des changements de plan + historique `_plan_reviews` (MAJ le plan, affûtage, pilote automatique). **Titre toujours accordé à la consigne** (`prTitleFor(titre, consigne, type, ancienneConsigne)`, plan-review.js : « + accélérations / lignes droites / strides / éducatifs » retiré quand la consigne dit « sans … » / « sans intensité » ou qu'une nouvelle consigne ne les mentionne plus ; séance devenue facile avec un titre de qualité → « Footing EF » / « Sortie longue », l'inverse → « Fractionné » / « Tempo » ; course jamais touchée) : appliqué par `prApplyChanges` après chaque changement (entrée `field: 'title'`, `kind: 'coherence'`, annulée avec le reste — `prUndoReview` annule dans l'ordre inverse), par le générateur (`generateAthletePlan`), au lancement sur le plan en cours (`prTitlesCoherent`, plan-daily.js, séances faites comprises — seul le titre change) et côté serveur sur les changements du Coach (`planCleanChanges` → moteur, règle « TITRE ET CONSIGNE COHÉRENTS » dans `PLAN_PRINCIPLES`).
