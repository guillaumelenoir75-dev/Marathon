# Plan Marathon — contexte projet

PWA de préparation marathon, multi-utilisateur. L'admin crée les comptes et a accès au Coach IA. Les athlètes suivent leur plan.

## Stack
- **Frontend** : `public/index.html` — HTML + CSS inline, charge 23 scripts JS via `<script defer>`.  
  Build : Vite (`root: 'public'`, `publicDir: '../public-static'`) → `dist/`. Les fichiers `public-static/src/*.js` sont copiés verbatim (pas de hash), chargés en scripts classiques (pas de modules ES). Toutes les fonctions doivent être en scope global.
  **Chargement** : `scriptFiles` (vite.config.js) → un seul `bundle-<n°>.js` ; écrans rares → `lazy-<groupe>-<n°>.js` (`lazyGroups` : `course` = race-nav-data + race-nav + race-map, `progress` = prep-progress, `whatif` = plan-whatif), adresses dans `window.LAZY_BUNDLES` injecté dans dist/index.html, chargés par `lazyLoad(g)` (config.js) depuis des points d'entrée du même nom que la vraie fonction (`initRaceOrgMap`, `openProgress`, `openWhatIf` → `_lazyCall`) ; en dev, fichiers sources. Un module à la demande ne doit être appelé que sur action (jamais au démarrage) ; ses scripts ne sont pas dans index.html. Cache (firebase.json) : `/src/@(bundle|lazy)-*.js` = 1 an `immutable` (nom unique par version), le reste de `/src` sans cache. Chart.js en `defer`.
- **Backend** : Cloud Functions Firebase v2 (Node 24), modulaires dans `functions/`.
- **Données** : Firebase Realtime Database, projet `prepa-marathon` (europe-west1). Structure : `users/{uid}/state`, `users/{uid}/role`, `users/{uid}/preps/{id}` (copie figée d'une prépa) + `users/{uid}/prep_index/{id}` (fiche : nom, date, temps, bilan), `users/{uid}/prep_next` (prépa à venir : `meta` + `state` = clés de prépa, modifiable avant son début), `_push_subscribers/{uid}`.
- **Auth** : email / mot de passe. Création de comptes réservée à l'administrateur (ADMIN_UID).
- **Hébergement** : Firebase Hosting → https://prepa-marathon.web.app
- **Sécurité DB** : règles dans `database.rules.json` — chaque user ne lit/écrit que ses propres données, l'admin peut tout lire/écrire.

App : `stravaHistSync` (tâches du jour, une fois par jour ; `true` = tout réimporter, Compte › « Historique Strava » `openStravaHistory`), `prStravaHistLoad` (dans `prPrefetch`), `prStravaSessions` (type : course si `w`=1, longue si `w`=2 ou ≥ max(16 km, 1,6 × médiane), séance si `w`=3, sinon footing ; `s.ext`) fusionnées dans `prAllDone` sauf si une séance de l'app existe le même jour à ±8 % de km ; `prStravaRaces` (courses marquées « course » de 5 / 10 / semi / marathon, temps écoulé) → `prKnownRaces` (niveau) et `prepBestTime` (records ; la course qu'on enregistre est exclue) ; non comptées dans la série ni dans « déjà validée » ; listes de Statistiques : 12 derniers mois.
**Forme / fatigue** (`fitness-model.js`, carte `#fm-card` de Statistiques) : modèle de Banister — charge TRIMP par séance (`fmTrimp` : minutes × FC de réserve × 0,64 e^1,92·FCr, FC repos = médiane 30 j ; sans FC, minutes × facteur du type), forme = moyenne exponentielle 42 j, fatigue 7 j, fraîcheur = forme − fatigue du matin (`fmRun`), sur tout l'historique (`fmLoads` via `prAllDone`) ; ajustement personnel niveau ≈ p0 + k1 forme − k2 fatigue sur les repères de `prFitness` (`fmLsq`, ≥ 8 repères sur ≥ 60 j, 0,8 ≤ k2/k1 ≤ 4, sinon k1 = 1, k2 = 2) ; projection jusqu'au jour J avec les séances prévues (`fmRaceDay`, `fmPlanned`), affûtage conseillé (`fmTaperBest` : dernières semaines — marathon 3, autres 2 —, facteurs non croissants ≥ 40 / 45 / 50 %, pénalité au-delà de +25 de fraîcheur ; proposé seulement à ≤ 35 j de la course avec forme ≥ 20 et ≥ 42 j d'historique) appliqué par `fmApplyTaper` → `prApplyChanges` (kind `taper`, annulable) ; simulation de la semaine suivante ±20 %. `prApplyChanges(sel, meta)` (plan-review.js) = application commune des changements de plan + historique `_plan_reviews` (MAJ le plan, affûtage, pilote automatique).
**Validation express** (`quick-validate.js`) : `/?action=validate` (raccourci iPhone, raccourci du manifeste) → dernière activité Strava rattachée par `qvMatch` (séance non faite à J-3 … J+1, même jour puis km les plus proches ; déjà validée = signalé) → validation pré-remplie (`_fetchAndApplyStravaDetail`) ; mode d'emploi Compte › « Validation express » (`openQuickValidateHelp`).
**Heure de coucher** : `bsBedtime` (body-signals.js, ligne du soir dès 18h sur la carte « Forme du jour ») et `bedtimePlan` (helpers.js, notification `bedtimeReminder` 20h30, `_bedtime_push`, préférence `notif_bedtime`) — même calcul : réveil 50 min avant une séance du matin (sinon 7h), besoin `_sleep_target_h` (8 h), + moitié de la dette des 3 dernières nuits WHOOP (1 h max), +15 min avant une séance clé, 15 min d'endormissement.

**Historique complet des analyses** : toute analyse (charge, dérive, foulée, zones FC, niveau `prFitness`, allure EF réelle `prObservedEf` / `getBestEfPace` / `calcMarathonPace`, prédiction `buildMarathonPrediction`, contexte du Coach `_ccHist`/`_ccMonthly`, comparaison après validation, série, Statistiques › séances et performances) lit **tout ce qui a été couru depuis la 1re séance enregistrée**, toutes prépas confondues : `prAllDone(today)` (plan-optim.js : prépa affichée + prépa en cours réelle + copies `preps/*` chargées par `prPrefetch()` dans `_prAllSnaps`, sans la copie de la prépa en cours, dédoublonné date | type | km, `s.cur`, `s.hard`, `s.gw` = n° de semaine continu ; cache 1 s vidé par `save()` via `prHistoryChanged`) et `prDoneLog`. Ne plus boucler sur `getOrderedWeekSessions(1..CW)` pour une analyse. Copie consultée en lecture seule : ses seules données. Côté serveur, `buildTrainingSituation` ajoute les séances des prépas terminées depuis ≤ 42 j (charge 7/14 j, dernière séance) ; allure EF des briefs = `_ef_ref` (calculée par l'app sur l'historique, écrite chaque jour par `prepDailyTasks`, `efRefOf`) ; plafond EF `efMaxOf(state)`.

**Plan de l'admin** : `usesHardPlan()` (firebase.js) = admin qui suit encore le plan Seine-Eure écrit en dur (config.js : `weeks`, `CW`…). Après « Nouvelle prépa », `state._plan_engine='generated'` : l'admin suit le moteur de plan généré (comme les athlètes) en gardant ses droits (`isAdmin()`). Les tests liés au plan utilisent `usesHardPlan()`, les droits admin `isAdmin()`. Les migrations admin (régénération du plan Seine-Eure) ne tournent que si `usesHardPlan()`. Pour une prépa générée, `syncPlanCompat()` (config.js) remplit `CW`, `weeks` et `weekDates` à partir du programme (extra_w*, meta_w*, plan_start_date) : le Coach IA, les stats et la validation suivent la prépa en cours. Utiliser `prepRace()` (course objectif), `planTotalWeeks()` et `isRecoveryWeek(ws)` au lieu de valeurs Seine-Eure écrites en dur. Km des chaussures : toujours `shoeKmTotal(nom)` (shoes.js) — table Seine-Eure en mode dur, sinon report `shoe_km_*` (figé par `prepApplyNew`) + séances faites de la prépa. Côté serveur : `getCurrentWeek(state)`, `adminCurrentWeek(db)`, `getPrepInfo`/`prepObjectiveText`, `weekTypeFor`, `loadPrepState` (helpers.js). Vision complète pour le Coach : `buildTrainingSituation(db, state, today)` (helpers.js) — prépa en cours (semaine, phase, J-x), dernière course + période post-course (≈ 1 jour par mile : marathon 26 j, semi 13 j, 10 km 6 j), prépa suivante (`prep_next/meta`), courses (`prep_index`), records, zones FC recalées (`_hr_zones`, prioritaires sur les 140-148 bpm écrits dans les consignes), signal de la foulée récent (`_body_signals`, ≤ 3 j), charge 7/14 j, séance du jour avec sa consigne ; injectée dans les briefs du matin (`briefAfterFcRepos`, `generateMorningBriefContent`, `morningBrief`, `quickBrief`) et le chat (`coachChat`).

## Tests (filet de sécurité avant chaque déploiement)
- `npm test` : tests unitaires (`tests/unit/`, moteur de l'app chargé tel quel par `tests/helpers/frontend.js`) et serveur (`tests/server/`, Cloud Functions avec doublures Firebase / IA / push via `tests/helpers/functions.js`). `node --test`, sans dépendance.
